# Account deletion design

Scope: R04 at base `1fc87cf0ebad338cbdb791e1c266fac08f98ce90`, coordinated with R03, R05, accepted R07, R08/R09 generation writers, and R23 billing recovery. The release owner accepted this design for implementation; no retention duration or identity-erasure authority is inferred.

## Required outcome

A deletion request must durably fence the account before taking inventory. Every subsequent commit must either belong to the exact still-active account generation, be an explicitly authorized deletion-job step, or be an explicitly classified retained audit/billing-containment write. A delayed request, AI result, browser replay, account recreation, retry, or second server must not recreate deleted active data. Interrupted stages must resume using durable state. Incomplete inventory, unknown remote cancellation, unverified asset ownership, and unapproved retention policy must remain visible pending/manual states.

## Chosen architecture

1. `accountLifecycles/{uid}` is a separate durable control record with a random immutable account generation, state `active`, `deleting`, or `deleted`, and the deletion job identity when applicable. It survives removal of `users/{uid}`. Account generation is compared by exact equality, never by a timestamp or only an active/deleting boolean. Registration and lifecycle initialization happen transactionally. This release exposes no automatic deleted-UID recreation; an eventual reviewed reopen must allocate a new generation and cannot erase the old job history.
2. Authenticated route execution establishes an immutable request generation scope before downstream work. Use a small AsyncLocalStorage boundary rather than adding an optional parameter to every deeply nested writer and silently missing a caller. Route coverage is enumerated and tested; two concurrent requests must prove scope isolation. The scope originates from independently verified identity and durable lifecycle state. A client generation claim is a concurrency precondition, never authentication proof. New managed session markers include generation, and client state is invalidated when generation changes. Legacy claims cannot authorize a reopened account generation.
3. The shared document-store commit boundary adds lifecycle reads to the same transaction as owned mutations, validates scope generation, and checks deletion state. Direct puts, creates, batches, course patches and commits use this boundary rather than bypassing it. Ownership comes from trusted account paths and audited ownership fields/course author records; mutable payload fields cannot override an existing owner's fence. New explicit scopes for deletion-job operations and verified billing containment have restricted write sets and must match durable job/generation state. There is no generic public bypass flag.
4. `accountDeletionJobs/{jobId}` stores UID, generation, status, current stage, progress/cursors, retry identity, billing identifiers and cancellation state. The initial fence and job creation are one transaction. Job stages are checkout containment, complete inventory, Stripe reconciliation, course/share/document removal, exclusive Blob cleanup, final inventory verification, and retention review/finalization. Repeating an acknowledged stage is safe; an unknown external result remains unknown until independently read back. A second request resumes the same job, including after the account document is removed, using recent verified identity.
5. Inventory must prove completeness for every account collection, authored course and dependent record class. Bounded traversal that overflows records a durable manual-review outcome and a contact/reference; it never returns `deleted: true`. Current authored-course list limits and course-dependent query truncation need explicit guards. Unknown account subcollections must be detected by a bounded prefix scan or equivalent store inventory, not silently omitted by a fixed list. The final scan distinguishes declared retained records from undeclared active records.
6. Stripe cancellation is permitted by R23 `apiReady`, independently of Portal and new checkout. The job records stable UID/customer/subscription identifiers before remote work. The existing ownership verification, open-session containment, subscription enumeration and timeout readback remain. An unconfirmed cancellation retains the account/job/identifiers, returns a resumable pending status and makes no deletion-complete claim. Paid-path acceptance waits for R23 tests.
7. Export, job response, profile recovery copy and Privacy Notice use one retention inventory. Existing identity mappings, legal/billing consent, safety/enforcement records and deletion control records are disclosed. Exact retention durations/holds are an owner/privacy-review gate; no invented duration or broad audit erasure is implemented. Until approved policy is supplied, the job must truthfully distinguish active-data removal from pending retention/manual review rather than claiming complete erasure.

## Considered alternatives

Only adding a deletion check to `requireAcceptedAccount` is insufficient because requests can wait on AI or I/O after authorization. Passing optional generation arguments through every store helper is explicit but leaves old call sites silently unfenced; mandatory arguments require broad interface churn and still need global target-account ownership checks. The chosen request scope plus shared commit fence keeps generation immutable through nested async work and makes missing ownership coverage testable at one boundary. Its main risk is a missed route/system scope, addressed by writer coverage and real route races before integration.

## Verification sequence

Start with real mastery PUT paused immediately before its actual datastore write, delete the same seeded account through the real DELETE route, then release the write: the old implementation returns 200 and recreates learning data. The fixed route must reject it with no resurrected record. Expand this fixture to paused transactional evidence, notes/progress/credits/shares, late AI settlement and course/banner completion. Use the real local datastore and route code, substituting only pause points and external providers; do not call these PostgreSQL tests.

Add stage interruption/resume fixtures, concurrent deletion callers, unknown Stripe outcomes and retry readback, inventory overflow/unknown records, shared vs exclusive Blob ownership, retained-policy reporting, and exact-generation ABA tests. Add a real PostgreSQL fixture using the release verification environment/CI when available. Preserve R03 behavioral browser cases and add deletion/reentry invalidation. Root owns shared suite registration, integrated review, hosted/CI evidence, and all remote operations.
