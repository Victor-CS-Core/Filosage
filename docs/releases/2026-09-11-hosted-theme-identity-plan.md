# Hosted appearance and identity continuity plan

Status: proposal for owner review, September 11, 2026. Source baseline: `6403509`. No authentication implementation, registrations, secrets, tenant changes, accounts or deployment were performed. The existing [appearance audit](../AUTH_APPEARANCE_AUDIT_2026-09-11.md) records the earlier read-only Azure evidence; this document does not claim that configuration was inspected again.

## Recommendation and acceptance boundary

Prototype two application-specific branding clients while retaining Easy Auth. Reuse the existing explicit proof-of-both-identities transaction, with a separate client-bound intent version. This is the narrower path to changing the actual Microsoft-hosted pages. It is not safe to add two client IDs and immediately route all customers through them.

The alternative is native authentication under the original client ID. That can preserve the existing identity key, but its browser/session integration is unproven here and it renders app-owned UI. It does not fix the Microsoft-hosted fallback pages. Do not select it as evidence of hosted parity without an explicit change to the product acceptance requirement.

Success means explicit light works on a dark OS and explicit dark works on a light OS throughout hosted sign-in, signup, email-code entry, recovery and error states. System preference resolves immediately before departure. Existing canonical UID, account generation, course ownership, progress, legal acceptance and subscription binding must remain unchanged. Anonymous users still get catalog/outline only; verified identities without completed registration still cannot fetch lesson bodies, practice or progress.

The storage adapter already supports an atomic mapping write plus intent consumption. The missing work is verified client identity, source/target-specific proof, new-schema readers and recovery routing. No bulk account or billing migration is needed for an already-proven link.

## Option A: branded clients with explicit identity binding

Microsoft supports application-assigned themes and per-theme CSS in external tenants, with up to five themes. Use fixed light and dark CSS; the light stylesheet must not contain an OS-dark override, and the dark stylesheet must not depend on one. Keep accessibility, forced-color and reduced-motion rules. Application assignment selects the theme, not a locale parameter. [Microsoft application branding documentation](https://learn.microsoft.com/en-us/entra/fundamentals/how-to-customize-branding-themes-apps). External ID is excluded from the workforce-tenant CSS retirement described in the [CSS reference](https://learn.microsoft.com/en-us/entra/fundamentals/reference-company-branding-css-template).

Microsoft documents different `sub` values for different client IDs and stable object identity through `oid` within a tenant. Matching email must never grant access. This plan uses explicit proof of both sessions; it does not introduce automatic cross-client `oid` migration. [Microsoft ID-token claims reference](https://learn.microsoft.com/en-us/entra/identity-platform/id-token-claims-reference).

### Proposed server contracts

All names below are proposed, not existing configuration.

1. Add a server-only connection map: `filosage` (original), `filosagelight`, `filosagedark`. Each entry fixes `clientId`, `issuer`, discovery URL and enabled state. Retain the public provider family `filosage`; add verified internal `connectionId`/`clientId` fields to `VerifiedProviderIdentity`. Derive them from the allowlisted sidecar provider and configured registration, never browser input. For new connections require matching trusted `aud` and exact issuer; if the principal does not expose audience reliably, stop the prototype until the platform validation evidence and adapter contract are resolved. Preserve all existing original-provider validation.
2. Leave Google/original `v1` hashes and document schemas byte-compatible. New-client keys use `identityLinks/v2_<HMAC([v2, filosage, connectionId, issuer, clientId, sub])>`. New records contain exact `schemaVersion`, `keyVersion`, `identityHash`, `canonicalUid`, `provider`, `connectionId`, `clientId`, `createdAt`, `updatedAt` fields; the store injects its existing `id`. Continue using the existing email-owner index for collision detection. Do not mutate canonical account documents or copy entitlement data when linking.
3. Add `/api/auth/link-intent/v2` and `/api/auth/link-intent/v2/complete`, leaving the current Google-to-original endpoints intact. Creation accepts only an allowlisted target connection and a safe return path. The server supplies all source identity fields from fresh authentication and an existing legally ready account.
4. The exact v2 intent records `schemaVersion`, `keyVersion`, `canonicalUid`, `accountGeneration`, `sourceIdentityPath`, `sourceIdentityHash`, `sourceConnectionId`, `sourceAuthTime`, `targetConnectionId`, `targetClientId`, `targetIssuer`, `emailHash`, `returnPath`, `createdAt`, `expiresAt`, `usedAt`; consumption adds `updatedAt`. Paths and identifiers are validated, not accepted as arbitrary datastore locations. Use a new HMAC token namespace and `filosage_identity_link_intent_v2` cookie restricted to the v2 completion API, retaining Secure/HttpOnly/SameSite=Lax and ten-minute expiry.
5. Creation rechecks source mapping, account generation and email ownership inside its transaction. Completion independently requires fresh target authentication, the exact target client/issuer, matching verified email as an additional constraint, unchanged generation/source mapping, and an unconsumed intent. Recheck everything inside the transaction. Create only the missing target mapping and consume the intent atomically. An existing exact mapping is acceptable; any conflicting owner fails without account changes. Support original-to-theme, theme-to-theme and theme-to-original explicit linking; a registered Google source can also enroll a theme. Do not retain the old Google `uid === subject` assumption for already-linked sources.
6. Add `/auth/complete-link/v2` with the current bounded completion/error UI behavior. The managed callback remains Easy Auth's callback; the app page is only its post-login destination. After successful linking use a full local navigation so session restoration reads the canonical mapping before learner requests resume. Retain strict response schemas, CSRF protection, durable rate limits, replay handling, account-generation checks and redacted audit events.

`identity-link-policy.ts`, `identity-link-server.ts`, `identity-types.ts`, `easy-auth-principal.ts`, `auth-runtime.ts`, `identity-client.ts`, `AuthProvider.tsx`, the new route/page handlers, and `infra/azure/main.bicep` are the concrete implementation boundary. Inventory/export/deletion and expired-intent pruning must recognize both namespaces. Keep old namespace readers for rollback. Do not change account-session marker semantics or bypass legal readiness.

### Entry, existing-account recovery and new accounts

Add a small separate `/api/auth/appearance-options` response and `/api/auth/appearance-entry` POST rather than adding unnegotiated fields to `/api/auth/session`. Entry accepts `appearance: light|dark` and a validated local return path; it returns only an exact enabled named-provider URL. Resolve system appearance in the browser immediately before this call. The server selects the connection. Keep the original provider and original v1 DTO usable by older clients.

For an enrolled customer, the themed identity resolves directly to the established canonical UID. Reauthentication may use an enrolled connection only; a theme switch is not permission to link an unknown identity.

For an unbound themed sign-in, block private data and account creation when the verified email belongs to another account. Offer the existing Google method or original email-code method, using fresh authentication to recover that account. Preserve only the desired appearance and safe return destination across this navigation. Once the established account is authenticated, create the v2 intent and authenticate the selected themed target again. The two authentications, not email equality, authorize the mapping. If either original method is unavailable, proof is stale, email has changed, or mappings disagree, fail closed and retain existing support recovery; do not create a replacement paid account.

The initial prototype disables new account creation through themed clients. Full release additionally needs an explicit v2 registration path: a genuinely new verified identity can create its canonical account only in the existing legal-acceptance transaction, with an unowned email index, no conflicting subject/account record, and its v2 link written atomically. Preserve the existing subject-based creation convention and collision guards; never overwrite an established account. Later theme/original links point to that same UID. New users cannot enter private learning before that transaction succeeds, and linking alone never records consent.

An original-provider recovery visit can still show OS-based appearance until the new client is linked. This is a real first-use limitation of this option, not completed manual parity. The owner must either accept a clearly described one-time recovery exception or require an additional reviewed solution before declaring every hosted step compliant. Do not silently count only the final themed page as success.

### Required administration and rollout

The owner/admin must approve two client registrations in the existing external tenant, association with the reviewed existing user flow, two fixed branding themes and exact theme assignments. Required roles are Organizational Branding Administrator plus Application Administrator for assignment/registration, and appropriate user-flow administration permission. No new tenant or customer account is required for the initial visual probe.

Container Apps supports multiple uniquely named OIDC providers. Each needs its own registration, secret reference and callback. Proposed production callbacks are `https://filosage.com/.auth/login/filosagelight/callback` and `https://filosage.com/.auth/login/filosagedark/callback`. Add only exact separately approved candidate callbacks, never wildcard return URLs. Use scoped `Microsoft.App/containerApps/authConfigs/write` and the existing secret-management workflow; keep secrets out of browser configuration and command logs. [Microsoft custom OIDC configuration](https://learn.microsoft.com/en-us/azure/container-apps/authentication-openid).

Deploy dual-version readers, validators, cleanup and disabled flags before configuring providers or exposing links. Treat each connection-to-client/issuer binding as immutable; never reuse a connection name for a different registration. Container App auth configuration is shared across revisions: first prove all traffic-serving and rollback revisions tolerate it. Then enable owner-only existing-account enrollment, followed by a small cohort. Enable new registrations only after their recovery/rollback evidence passes. Preserve the platform-owned authorization exchange, state, nonce and PKCE behavior; do not replace callback handling or enable weaker flow settings for styling.

Rollback first disables themed entry and new v2 registrations. Keep valid v2 mapping readers and configured providers available for customers already enrolled, especially new accounts whose only proven method is themed. Do not roll back to a revision that cannot read those identities, delete mappings, rotate their HMAC key, or remove their only sign-in method. Theme-to-original explicit enrollment allows eventual retirement of extra providers. Identity evidence and account-generation fencing remain authoritative through either direction.

## Option B: original-client native UI and a session bridge

Microsoft's JavaScript native SDK supports email-code and password signup/sign-in, including a React/Next sample. It requires enabling public-client/native flows, the associated user flow and a CORS proxy. Reusing the exact original client ID should preserve the pairwise identity according to Microsoft's client-scoped `sub` rule, but that must be demonstrated with real issued tokens before account lookup. Enabling public flows on the existing confidential registration also needs explicit compatibility review. [Microsoft native SDK quickstart](https://learn.microsoft.com/en-us/entra/identity-platform/quickstart-native-authentication-single-page-app-sdk-sign-in).

The current repository has no native token/session bridge. Container Apps documents client-directed login returning an `authenticationToken` used with `X-ZUMO-AUTH`; its concrete payload table covers built-in providers, not this custom `filosage` provider. That is not a guarantee that posting a native token to `/.auth/login/filosage` creates the browser cookie our routes require. Do not repurpose `aad`, trust a decoded token or forge sidecar headers to bridge the gap. [Microsoft Container Apps authentication flow](https://learn.microsoft.com/en-us/azure/container-apps/authentication).

If the owner chooses this alternative, the smallest investigation is the official sample against the original client on an approved candidate origin, plus a read-only diagnostic that reports only validated equality of issuer/client/sub/canonical UID and presence of recent-auth proof. Test the documented session exchange only after confirming custom-provider support with Microsoft. A successful token response alone is insufficient: reload, `/api/auth/session`, protected API calls, reauthentication, signout and account switching must all work with the real managed session boundary.

If that exchange is unsupported, the concrete fallback within this option is a separately reviewed application session: proposed `/api/auth/native/start`, `/continue`, `/session` and `/logout` endpoints, a same-origin allowlisted native-API proxy, and an opaque Secure/HttpOnly host-only session cookie. The server must own a one-use flow binding to native continuation state, validate signature/issuer/original audience/lifetime with trusted keys, resolve the existing v1 registry and retain generation/recent-auth fences. It must not accept an unbound browser-supplied JWT as login proof. Token retention, refresh, revocation, CSRF and precedence with Easy Auth need their own contract; a raw token in localStorage or an arbitrary forwarding proxy is not acceptable. This is substantial new session infrastructure, so it is not the recommended first prototype.

App-owned native pages can consume `ThemeProvider` directly. Social-provider and required web fallbacks remain separately hosted; their behavior and theme coverage must be measured and stated, rather than included in a blanket parity claim. Microsoft explicitly documents the browser step for native social sign-in in its [authentication approach comparison](https://learn.microsoft.com/en-us/entra/external-id/customers/concept-choose-authentication-approach).

## Smallest prototype and release evidence

1. **Hosted visual probe, no account mutation:** after approved admin provisioning, navigate a separate guest browser to each candidate named provider. Capture actual CIAM sign-in and signup-entry screens with the app light/OS dark and app dark/OS light. Inspect served CSS and application selection, contrast, logo, keyboard controls and mobile reflow. Do not submit an email/code or create an account. This can disprove the branding assumption before any identity code changes.
2. **Identity prototype, separate approval for existing test-account sign-in:** implement only disabled v2 binding and enroll one existing owned test account through original-to-light-to-dark. Require the owner to authenticate; no invented identity data. Record redacted equality results for canonical UID, generation, plan source/Stripe binding, consent and course ownership. Compare stored records before/after: only new mapping/intent records may change. No purchase or production account creation is needed.
3. **Required local regression matrix:** preserve all current v1 tests; add original/theme and Google/theme proof, wrong client/issuer/audience, swapped target, missing/stale authentication, token replay, concurrent completion, account deletion/generation change, email collision, new-registration denial/consent, and conflicting mappings. Verify registry hashes remain unchanged for old users, strict old session DTOs still parse, and forward/rollback readers support enrolled users. Extend the selected-lesson return and held-response A-to-B tests with zero guest/private reads.
4. **Hosted completion gate:** real permitted email-code, signup, cancel/error, expiry, original-account recovery and logout must pass across both opposing OS preferences and mobile engines. Any production signup or writes need separately scoped authorization. Confirm the chosen lesson returns only after registration/consent and the account retains its entitlements. Mock redirects, local fixtures, a CSS upload, token decoding or portal preview alone do not satisfy this gate.

Owner review can now authorize the two-client visual probe independently of the proposed identity contract. External blockers are the new registrations/theme assignments/candidate callbacks and an authorized existing test-account session for proof. No claim of a completed hosted theme fix is made by this plan.
