# Generated lesson writer protocol and cutover gate

This source introduces additive lesson write protocol version 1. It is not evidence of a hosted rollout or compatibility with an earlier production binary.

Every writable revision must enforce the R04 account-generation transaction fence, R07 publication proof binding, R08 immutable AI attempt/original-period accounting, and R09 generated lesson commit guard. A lesson save requires a current actor, account generation, canonical request identity and target payload, matching attempt token, finite request and resource lease, original accounting paths, current private publication state, scoped curriculum/source fingerprint and expected target content. The transaction writes the lesson, any evidence downgrade, exact result receipt and all accounting together. V2 pause and moderation quarantine are checked against current state at commit.

Additive fields are `usagePeriods.resourceLocks[sha256(courseId:lessonId)]` (request ID, attempt token, lease), `aiRequests.lockKey`, immutable attempt `lockKey`, `aiRequests.lessonResult` (version 1, course/lesson IDs, content and scoped course fingerprints, publication state, commit time), and `courses.lessonWriteEpoch`. Existing shared period quotas, personal budgets and global budget shards remain authoritative. Existing unscoped requests still use the original period lock; new lesson requests cannot bypass an active unscoped writer, and a new unscoped request checks resource locks. Same-key records created under a different locking protocol fail closed for reconciliation. Terminal observed attempt/global receipts make late finalization idempotent. A replay verifies its original lesson and course binding; a newer edit yields `IDEMPOTENCY_RESULT_SUPERSEDED`.

All publication/unpublication mutations in the supported writer advance `lessonWriteEpoch`; publishing with an already completed mutation key preserves the existing replay rules. The separate publication-state fingerprint detects private → public → private changes even when curriculum content returns to the same value. Targeted repair also carries that state and verifies current author/cohort policy inside the store transaction. Legacy courses remain readable; they do not acquire V2 repair eligibility.

## Required release sequence

1. Inventory every image, revision, worker and maintenance command able to write these records. Record full image digests and source SHAs. Identify outstanding course/lesson requests, attempts, accounting receipts and publication/repair mutations through approved read-only inspection.
2. Test the actual previous production image against disposable new-schema records while the candidate image exercises the same records. Cover stale lesson generation, deletion, publication ABA, replacement attempts, independent resources and accounting reconciliation. Different feature cohorts within the new binary are not this test.
3. If any existing writer is unknown or cannot honor the protocol, use an explicitly authorized write-quiescence window. Stop accepting new authoring mutations in all old writers; drain bounded in-flight calls and maintenance. Reconcile known terminal results and retain uncertain provider cost. Do not delete active attempts or infer a safe refund from a missing response.
4. Keep the new revision at zero public traffic while testing the frontend and BFF in the same Azure Container App. Only a separately authorized traffic change may make it active. Permit writes only after all writer inventory entries are compatible or quiescent. There is no separate QA application.
5. Roll back writes only to a proved compatible image. If no compatible rollback image exists, keep authoring quiescent during rollback; serving old code is not permission to let it mutate the new records. Retain additive records and audit receipts.

Minimum safe writer version is defined by the complete reviewed candidate SHA/image digest and the passed protocol tests, not by an environment variable that an old binary could ignore. No mixed-version write, migration, production mutation, traffic switch, old-image compatibility run, or rollback exercise was performed by this source change. Actual PostgreSQL 16 execution, previous-binary compatibility, zero-public-traffic candidate validation and authorized cutover remain separate gates.

Durable lesson provider stages/status/resume and evaluation spend-cap composition are subsequent integration work. This transaction protocol alone does not advertise those capabilities or claim background completion.
